## 一 · 🔴 核出一件实质问题：**技能包数据的天数是过期快照**

### 证据（全部开实物）

**① 技能包源数据现状**：
```
技能包_时间表查询官\data\timetable.json
  meta.version = v1.0.17 ｜ data_date = 2026-10-11 ｜ built_at = 2026-10-11 09:40
  文件 mtime   = 10-11 09:39（距今 2.5 天）
  家数 = 131
```

**② 用今天（2026-10-14）重算 `days_from_today`**：
```
不一致：107 条 / 131
  例：中国农业发展银行  截止 2026-10-11 ｜ 表内 0  ｜ 实际 -3
      中国有色矿业集团  截止 2026-10-11 ｜ 表内 0  ｜ 实际 -3
      快手             截止 2026-10-12 ｜ 表内 1  ｜ 实际 -2
      浙江省储备粮      截止 2026-10-14 ｜ 表内 3  ｜ 实际  0
```

**③ 状态字段同样过期**：
```
表内 status：进行中 112 ｜ 已截止 19
实际（10-14）已截止：23 家
→ 少算 4 家
```

**④ 而 Skill 设计上确实要用这个字段**（`fields.json` 行 88–91）：
```json
{ "key": "days_left",       "cn": "剩余天数",
  "desc": "Excel 活公式原文，供留档；技能回答请用 days_from_today" }
```
**→ `days_left` 只是留档，但 `days_from_today` 是"技能回答用的"，同样预存 → 同样过期。**

### 结论

> 🔴 **技能包 v1.0.17 的 `data/timetable.json` 预存了"距今天数"，值是 10-11 算的。**
> **今天（10-14）全部偏 3 天；`status` 少算 4 家已截止。**
> **→ 若 Skill 上线跑这份数据，回答「还剩几天 / 还能不能投」会答错 3 天。**

### 🔴 对照：另一份数据的设计是对的

```
_协作\timetable.json
  meta.版本 = v1.0.17-rebuild-20261013 ｜ 重建日期 2026-10-13 ｜ 家数 131
  字段：企业名称/截止日期/企业性质/银行类型/招聘方向/工作地点/学历/来源可信度/来源说明/投递入口/备注/线别/核验日期/待核
  🔴 【没有 days_left / days_from_today / status】
```
**→ 它只存「截止日期」原始值，天数由使用方实时算 —— 这才是不会过期设计。**

### 建议（**供主运营裁定，我不改**）

| 方案 | 做法 |
|---|---|
| **A（推荐）** | **Skill 回答时按当前日期实时算天数** —— 数据只存 `截止日期`，不存天数 |
| **B** | 保留预存天数，但**每次发布前重算**（并把重算写进发布检查） |
| **C** | 技能包数据源改为 `_协作\timetable.json`（它已是正确形态） |

## 一 · 先给结论

1. 自动任务的提示词是**每次触发时按配置投递**的，并带工作目录 `cwds` → **提示词本身就是记忆载体**。
2. 所以「会话没有记忆」不是故障，而是**默认前提**。方案不是让会话记住，而是**把记忆放到磁盘上**。
3. 项目里已经有现成的四个记忆落点（都已存在、可直接读）：

| 落点 | 文件 | 作用 |
|---|---|---|
| 唯一推进源 | `_协作\推进看板-2026-10.md` | 谁在做什么、卡在哪、指标、可复用点区 |
| 协作纪律 | `_协作\AGENTS.md` | 分工、禁区、冲突优先级 |
| 卡号索引 | `_协作\卡索引.md` | 发卡前必查，禁凭记忆递增（W-1） |
| 幂等凭据 | `_协作\自动化运行日志.md` | 今日同类任务是否已跑过 |

4. 🔴 **未验证项（诚实标注）**：**我无法从当前环境取证**「自动化触发时形成的会话是否继承上下文」。`automation_update` 的 view 只返回「ready to open」，不返回提示词正文；在 `%APPDATA%\CodeBuddy CN` 与 `%USERPROFILE%\.codebuddy` 下也未找到可读的本地存储（实查无命中）。→ 因此本启动包**按「不继承」这个最坏假设设计**，继承与否都不影响它成立。

## 五 · 「会话到底有没有记忆」——一次性可证伪实验

不要靠感觉判断，做实验。

1. 在有记忆的这一轮，选一个**只在本轮出现过的字符串**当哨兵，例如 `SENTINEL-20261016-C`。
2. 在任一条自动任务提示词的**末尾追加**一句：

```
【自证】本次回答开头先输出一行：
SESSION_PROBE=<你能否看到本轮之前的对话内容：能／不能>
SENTINEL=<除本提示词之外你已知的哨兵字符串；不知道就写「未知」>
```

3. 首次触发后看 `_协作\自动化运行日志.md`：

| 结果 | 结论 | 后续做法 |
|---|---|---|
| 写「能」且答出哨兵 | **继承上下文** | 可把长指令放在对话里说一次，提示词只留指路 |
| 写「不能」或「未知」 | **不继承** | 本启动包就是唯一出路（已按此设计） |

4. 验证完把这段 `【自证】` **删掉**（「只增不删」约束的是产物，不是提示词里的探针）。

> 为什么用哨兵而不是问「你记得吗」：问「你记得吗」得到的答案不可证伪；哨兵字符串**答不出就是没记忆**，没有中间地带。

## 六 · 降级方案（万一自动任务跑不动工具）

| 情形 | 降级动作 |
|---|---|
| 有上下文但无工具／无文件权限 | 只把「本次要做的 3 件事」写进日志，**不假装执行**；由下一次有人读卡时补做 |
| 无上下文也无工具 | 退化为**写唤醒信号**：在 `_协作\_wake\YYYYMMDD-HHMM-<角色>.md` 写一行「该起了」，并登记到看板「待执行队列」；任何有能力的会话读到即执行 |
| 提示词被截断 | 提示词只保留「通用前缀 ＋ 一行任务名」，**任务细节全部放磁盘**（看板在办清单 ＋ 对应 SOP 文件），提示词只负责指路 |

> 关键判断：**提示词越短越稳**。凡是能写进磁盘的，就不要写进提示词——磁盘不会截断，提示词会。

## 七 · 本方案最可能失效的地方（自曝）

1. **最大的坑是把「自包含」做成「自说自话」**：提示词写得再全，如果第 0 步没真的去读盘，它就会按自己的想象开工——这正是 R6（把看板当现行）的高发场景。所以「第 0 步读盘」必须是硬性第一句，且留痕里必须能看出它读了哪些文件。
2. **「无变化」会被当成「没问题」**：幂等日志里连续写「无变化」可能掩盖真实故障（例如读盘路径写错）。→ 因此「无变化」必须附带**读了哪几个文件、各多少字节**。
3. **哨兵实验有一次性特征**：验证完即失效，不能长期当监控手段。
4. **W 侧仍由 W 自己的实例控制**：我只能把可粘贴文本交出去，**无法代 W 修改其任务配置**；W 未落实前，这条链仍是半通。

## 八 · 工具侧实测补充（2026-10-16 · 推入 7 条提示词时顺手取到的一手事实）

1. **`mode=view` 的行为在两个实例上不一致（2026-10-16 修订）**：
   - **C 实例实测**（两次）：传入不存在的 id（`a6b`）也返回「Automation ready to open」，且**不返回提示词正文**；
   - **W 实例实测**（W 自报 WB191）：view **返回提示词全文**。
   → 结论：**该工具行为跨实例不一致，用一个实例的实测否定另一个实例的实测＝R1**。以**本方实例**实测为准。
   → **C 侧**：id 与正文一律靠 `suggested update` 回读 `created_at` 与对象确证（实测 `a6b` → `Automation not found`；`a6b49-9` → 有 `created_at`，才是真 id）。
   → **W 侧**：view 可返正文，故请把 4 条任务的原正文与前置后正文**各存一份到 `_协作\_automation_原文\`**，作为可核证据。
2. **`suggested update` 强制要求 `rrule` 与 `status`**：即使意图建一次性任务，缺 `rrule` 会报
   「missing required automation fields: rrule, status」，与工具说明里「EITHER rrule OR scheduledAt」不一致。
   → 变通做法：传 `rrule ＋ validFrom ＋ validUntil` 收窄窗口，工具会自动归一为 `scheduleType=once`
   （A6a／A6b 均已回读确认为 `once`，`scheduledAt` 分别为 2026-10-19T16:00 与 2026-10-22T09:00）。
3. **由此新增一条铁律（建议并入总账）**：**凡涉及自动任务的 id、调度、内容，一律以 `automation_update` 回读的任务对象为唯一权威源，
   看板与记忆记载只能作为索引**——这与守则 78（数字回权威源实跑）是同一个病根的第二次出现。
4. 🔴 **`mode=list` 也是跨实例不一致（2026-10-16 · 第三处，C36 §二·5）**：
   - **C 实例实测**：`mode=list` 直接返回 `unsupported automation mode: list`；
   - **W 实例实测**（WB195 §⑦）：`mode=list` 可用，返 6 条（id／name／status／scheduleType／rrule）。
   → 三处不一致汇总：① `view` 是否返提示词正文 ② A2b 时点认知 ③ `mode=list` 是否存在。
   → **总则（承本条第 1 项「以本方实例实测为准」再升一档）**：**凡工具能力，一律以本方实例实测为准；不得引用对方实例的行为反推本方状态或做本方设计。**
   → **两侧均实答「看不到运行态」**（W：view 只返配置态 ACTIVE/PAUSED，无 lastRunAt，列表不带运行时间；C：连 `list` 都不支持）
   → **「上次运行时间」这件事只能由 L 在 IDE 面板里目视**（C34 §四／C35 §九／C36 §四 同一件事，第三轮重复）。

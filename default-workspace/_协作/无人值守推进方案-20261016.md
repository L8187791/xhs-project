## 一 · 三条设计前提（决定了能自动到什么程度）

1. **自动任务只做四类动作**：清点、校验、生成草案、写卡。它不做判定、不发布、不触达、不花钱。
2. **判定权不下放**。凡是需要"发或不发""改或不改""接或不接"的决定，自动任务只把它写成「待判清单」，等 L。
3. **每次运行都留痕**。每次自动运行在固定日志文件里追加一行（时间、任务、做了什么、发现什么、写了哪张卡），用于防重复与事后追责。

> 这三条不是保守，是被错误逼出来的。总账里的 R1（用确定性措辞承载不确定依据）与 R3（为把内容写满而编）在无人值守时会放大：没有人打断，就容易把「未知」写成「已完成」。

## 二 · 资格清单（哪些事可以自动，哪些永远不行）

### 2.1 ✅ 可自动（白名单，不需要 L 拍板）

| 类别 | 具体动作 |
|---|---|
| **时效素材实跑** | 每日实跑主表，产出「今日/明日截止清单」原始输出，写进简报卡 |
| **发前复核** | 对已定稿但未发布的稿，复核「N 家」口径是否等于实跑结果、是否含唯一性断言、违禁词命中数、md5 与落档一致性 |
| **抽检** | 对 W 新交的稿执行二创、五查、闸门、违禁词、图内文字核对 |
| **主表字段维护** | 按既有自证四件套规则回写字段，附来源与等级，版本号递增，改前备份 md5 |
| **桌面与落档一致性** | 核对桌面待发包与 `_协作\发布包\` 的 md5，不一致即报警 |
| **回传入表** | L 回传的数据按口径入台账，缺项写待确认 |
| **周报草案** | 汇总单篇观看中位、评论率、回传缺口、卡片流 |
| **索引登记** | 新卡与自审文档的索引登记 |
| **库存与排期草案** | 生成排期建议表（不发布） |

### 2.2 🔴 永远不能自动（黑名单，任何情况下都不由自动任务执行）

1. **发布内容**。发布不经 AI 手，这是既有铁律。
2. **上架、下架、改价**。
3. **对外触达**：微信、私信、诊断包发送、任何形式的客户沟通。
4. **花钱**：保证金、报白费用、投放。
5. **主表结构性改动**：删字段、改字段类型、批量删记录。
6. **医疗与法律结论**。
7. **替 L 判定**「发或不发」「改或不改」「接或不接」「报价多少」。
8. **接新客户与新报价**。

### 2.3 🟡 灰区（需 L 一次性预授权才可自动，附授权语）

| 灰区动作 | 需要的预授权语（L 说一次，长期有效） |
|---|---|
| 当日截止数为 0 时，自动切换到备用素材 | 「A 层实跑为 0 时，允许自动改用 B 层素材，并在简报里标注」 |
| 稿件含唯一性断言且未发布时，自动应用删断言改写 | 「未发布的稿，删唯一性断言可直接改，改后须报」 |
| 桌面与落档不一致时，以落档为准覆盖桌面 | 「md5 不一致时允许以落档覆盖桌面并留痕」 |
| 违规词命中时自动删除命中句 | 「违禁词命中只删不重写，删后须报」 |

> 以上四条都是**有明确边界的技术动作**，不涉及对外与花钱，因此可以预授权。未获授权时，一律走待判清单。

## 五 · 卡片闭环（谁写、谁读、卡在哪）

1. C 侧自动任务产生**简报卡或待判清单**，写入 `inbox`。
2. W 侧自动任务读卡执行，写**回执**到 `outbox`。
3. C 侧下一次自动任务读回执，做抽检与登记。
4. **需要 L 判定的事项汇成一张「待判清单」**，只在这一处等 L，避免散落在各卡里。
5. L 回来后只需读一张待判清单与一份周报草案。

## 六 · 防失控设计

| 机制 | 做法 |
|---|---|
| **幂等** | 每次任务先读 `_协作\自动化运行日志.md`，若当日同类任务已跑过且无新输入，则只记录一行「无变化」，不重复发卡 |
| **待判隔离** | 需判定的不写进正文结论，只写 `待判清单` |
| **降频与暂停** | 连续 3 次运行结果为「无新事项」，自动任务降为每周一次，并在日志中提示 L 是否暂停 |
| **出错即停** | 任何一次自动任务发现自身产出与既有文件冲突，立即停止该次任务并写入冲突说明，不自行取舍 |
| **只增不删** | 自动任务不得删除或覆盖既有卡片，只能新增 |

## 八 · 本方案最可能失效的地方（自曝）

第一，**我无法验证自动化触发时形成的会话是否继承当前上下文**。若它不继承，所有提示词必须自包含，否则自动任务会读不懂自己该干什么。这一条必须在第一次试跑时验证。

第二，**W 侧断点未修之前，这个方案的自动程度只有一半**。C 侧会自动产出待判清单与卡片，但没有人自动读卡执行，卡片会堆在 inbox。

第三，**无人值守的最大风险不是跑错，而是跑出一堆看似完成的结果**。因此 §2.2 黑名单不是建议，是硬约束。
